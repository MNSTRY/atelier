# Build Harness

People establish the objective and acceptance criteria; agents implement admitted
work; owners review consequential decisions and actual delivery. Coordinate with
the user's existing coding, testing, review and CI tools. Fabric may consume the
coordination proposal; creating that proposal does not enroll or wake an owner.

## Bound the work

Establish purpose, owner, scope, acceptance criteria, required gates, admitted
effects, attempt budget and stopping rule. A dependency names the exact producer
artifact and the receiving need. Shared initiative membership creates no dependency
or authority. Keep independent work moving while a concrete prerequisite is absent.

Use `atelier harness build` and `@mnstry/atelier/build`, with the shared
`@mnstry/atelier/harnesses` records. `atelier build` retains its older projection
meaning. The reference example has simulated reviews and CI: never reuse its
approval reports as real evidence. If tooling is missing, prepare a plan and report
the gap without fabricating execution.

## Implement and verify

Reserve an isolated writer lane or follow the repository's existing custody
mechanism. Preserve local edits and do not claim another task's ownership.
Implement against the admitted inputs. Use existing tools to run appropriate
tests and actual review/CI workflows only within the task's authority.

The read-only Git adapter binds clean committed source and selected artifact bytes.
A writer declaration remains caller-reported. Record the exact commit, tree,
artifact digest, skill binding and evidence; a changed candidate needs new proof.

Persist an attempt intent before invoking an external executor. These records do
not invoke tools. On uncertain dispatch, preserve its identity and reconcile the
existing attempt before retrying. A completed transport or command does not satisfy
a review or CI gate. Keep unavailable, failed and passed evidence distinct.

## Integrate and return learning

Evaluate the current candidate, every required gate and current dependency
snapshots. Report missing evidence and candidate changes without treating stale
receipts as current. Review, CI, integration, delivery and recipient acceptance
remain distinct. Record only the actual owner's decision and observed delivery.
The harness reports consistency; repository and host controls enforce authority.

Prepare a coordination proposal for the existing owner/coordinator. Do not create
tasks, send messages, publish or deploy from a manifest alone. Emit an accepted
artifact handoff to Knowledge Harness, preserving assumptions, limitations and
the evidence behind the result. Research quality or business usefulness cannot
be inferred from a successful build.

When an upstream source changes, refresh dependency snapshots and prepare the
affected decisions for reconsideration. Route observed skill, tool, host, context
or provider problems through version-bound Steward feedback. Preserve unknown
causes and adopter consent; do not automatically rewrite or upgrade skills.
